I have no objection to your Gotify plan, but a few points on running it safely, and on whether the other ideas fit, are below.

### 1. Inventory

I've noted your LinuxGSM level as **advanced**, as you set it. In `surveys/README.md`, advanced means you design multi-part solutions, handle errors and edge cases, and others could rely on and maintain the result. Survey 2 will test the claim against that definition, so keep a `history` line when it moves.

### 2. Running the Gotify script

The script page says it runs in the Proxmox host shell and builds a container. So it executes **as root on the hypervisor**, which is the one place where a mistake has the widest effect. The page also lists Gotify version 3.1.1, and the release notes show the latest versions include security fixes, including a requirement for an elevated session when creating users. That is a reasonable sign that the script installs a recent version.

I could not read the script source itself, because GitHub blocks my access to its file pages. So the vetting is yours, and it takes about ten minutes. A habit worth building:

1. **Read before running.** Use the page's "Install source code: View" links. As far as I know, the project's layout has one script that runs on the host and one that runs inside the new container.
2. **Check what the host script pulls in.** As far as I know, these scripts load a shared helper file from the same repository each time they run. So you are trusting that repository's current state, not just the one script. If you want to freeze a known version, the site's "Pinned versions" section exists for that purpose.
3. **Red flags to look for:** downloads from any domain other than the project's own and Gotify's official release page, changes to files on the host (not just the container), SSH keys or `authorized_keys` edits, firewall rule changes, `chmod 777`, and any prompt about sending usage or diagnostics data. Choose deliberately if it asks.
4. **Prefer defaults that are conservative:** an unprivileged container, modest resources, and a fixed IP (or a DHCP reservation), so the URL in your phone app never changes.

### 3. Using Gotify once it's running

- Enter the URL the script prints at the end (not one from memory).
- **Change the default admin credentials immediately.** As far as I know, a fresh Gotify starts with a well-known default login.
- Create an **application token** for each sender (Proxmox, scripts), rather than sharing one.
- Test from the Client:

  ```bash
  curl "http://<GOTIFY_HOST>/message?token=<APP_TOKEN>" -F "title=test" -F "message=hello"
  ```

  The message should appear on your phone within seconds. Replace the placeholders with your own values, and keep the token out of logs and the repo.
- In Proxmox, look under Datacenter → Notifications for a Gotify target. As far as I know it exists in current versions, so please check and report what you see.
- Gotify is plain HTTP on the LAN to begin with. That is acceptable for a first test, and it connects to the certificate question below.

### 4. Your key insight: the notifier dies with the thing it watches

You're right, and it has a standard answer: **alert on silence**.

- A small recurring ping goes from Headless to an **outside** service. If the pings stop, that service alerts your phone by its own channel. As far as I know, services like healthchecks.io do this and have a free tier, but please check what is currently offered.
- It needs no inbound connections, so CGNAT is irrelevant. It also covers power loss, a hung host, and a dead Gotify.
- Alternatives are a second always-on device on the LAN (a cost, and one more thing to maintain), or the UPS tool described below, which only covers planned shutdowns.

Start with Gotify, then add the outside heartbeat once Gotify works. Two layers are enough.

### 5. The UPS

The standard tool is **NUT (Network UPS Tools)**: it monitors the UPS, sends a notification on power events, and tells connected machines to shut down cleanly in order. It also feeds Gotify, since NUT can run a command on events. Put it on the roadmap after notifications and backups.

### 6. Certificates, reverse proxy, and webmin: drawing the line

Your instinct, "just because I can doesn't mean I should," is the right test. A rule for every added service:

1. What problem does it solve **today**?
2. What breaks if it fails?
3. How many minutes a month does it cost to maintain?
4. Could I rebuild it from a short written recipe?
5. Is there a simpler 80% solution?

Applied to your three ideas:

- **The certificate warning:** as far as I know, Proxmox creates its own certificate authority. Telling the Client's browser or system to **trust that CA once** often removes the warning with **no new service**. It only works if the address you browse to matches the names in the certificate, so check that. This is the simplest option and my suggested first step. A proper certificate for a LAN name through Proxmox's built-in ACME support requires owning a domain name, so decide that later if at all.
- **A reverse proxy:** it solves "one address and one certificate for many web interfaces," which you don't have today. It also becomes a single point of failure and another service to update. **Not now.** Revisit when you have many web interfaces to protect, or once you resolve the outside-access question.
- **Webmin as a single pane:** one Webmin can control others, but it adds a root-level web admin to every machine, and the controlling one becomes a high-value target. As far as I know, Webmin has had serious vulnerabilities in the past. If you keep it, stay on the LAN, keep it updated, and disable it where you don't need it. Proxmox already has its own interface, so I'd reserve Webmin for machines that lack a better one.

Record each of these as a short decision (accepted or deferred, with your answers to the five questions). That is exactly what `docs/decisions/` is for, and it keeps "can versus should" from living only in your head.
