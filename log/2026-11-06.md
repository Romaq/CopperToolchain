The main constraint is that TLC can't see anything this project knows. Each Claude.ai project has its own memory and its own conversations. Whatever TLC needs to know about the customer relationship has to be written into files TLC can read. The decisions below follow from that.

### 1. How TLC finds out what tools exist (the "dynamic inventory")

TLC can't inspect this project, so the inventory has to be a published artifact.

- **Recommended:** generate a manifest, such as `docs/TOOLS.md` or `tools/manifest.yaml`, from the scripts themselves. Each script carries a header block (name, purpose, usage, version, status), and a small script collects them. The manifest then can't drift from the code.
- **Delivery:** the repo is public, so TLC's instructions can point to the raw GitHub URL of the manifest. TLC fetches it at the start of each session, so it's always current without you re-uploading anything.
- **Fallback:** upload a snapshot to TLC's project knowledge. This works, but it goes stale.

### 2. What the "customer" relationship means in practice

- **Direction of requests:** TLC asks for tools, and this project builds them. Decide where requests live. I'd suggest GitHub Issues or `docs/requests/`, with you as the courier between the two projects.
- **Ownership split:** you've already said modpack-specific work stays in TLC and generic tooling stays here. A one-line test helps: "Would a project other than TLC use it?" If yes, it's a request to this project.
- **Versioning and stability:** decide whether TLC pins to a tool version or always uses the latest. I'd keep it simple for now and use the latest, with a changelog line in the manifest.
- **Feedback loop:** TLC should report what worked or broke in a form you can paste back here.

### 3. What TLC carries from this project

TLC needs a portable instruction block. I'd put it in TLC's project instructions, because that's the one thing it reads every time.

- The log convention (`## 🤖 CLAUDE · Turn N · date`, user turns in blockquotes) and the rule that your numbering is authoritative.
- The public-log privacy caution you already use here.
- The customer statement, the manifest URL, and the request channel.
- A `docs/STATE.md` handoff file of its own, so fresh TLC conversations resume cleanly.

You already have `templates/new-project-kit/` and `docs/PROJECT-GUIDE.md` from the work for DJV22. Decide whether TLC gets that same kit or a leaner version, since TLC is your own project and not a separate person's.

### 4. Where TLC's logs and files go

- **Same repo, separate folder:** for example `log/tlc/`. This is easy and keeps one privacy hook, but it mixes the two projects' histories.
- **Separate repo:** for example a modpack repo. This is cleaner, and it fits your plan to release maintenance tools on GitHub for the modpack. But then the privacy check and sync scripts must be installed there too.

This is the biggest structural choice, so I'd settle it before TLC's first prompt. The modpack's eventual public repo may be the natural home for TLC's logs.
